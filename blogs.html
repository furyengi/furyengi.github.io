01AI infrastructure6 min read

What reliable AI gateways get wrong about provider failures

AI gateways often flatten every upstream problem into a generic server error. That makes applications less reliable exactly when they need the most context. Authentication failures, quota exhaustion, malformed requests, and interrupted streams are different failure modes and should remain different all the way back to the caller.

The useful approach is to preserve the provider signal, normalize it into a stable internal error shape, and test both buffered and streaming paths. A gateway should not merely forward traffic; it should help the application decide whether to retry, reconfigure, fall back, or stop.

02Systems design7 min read

Offline-first pharmacy software is really a data-integrity problem

“Works offline” sounds like a synchronization feature. In pharmacy operations, it is a promise that stock quantities, batches, expiries, and sales remain trustworthy even when connectivity disappears midway through a transaction.

That means FEFO deduction, local transactions, conflict handling, and eventual synchronization have to be designed together. The interface can recover from a network failure; incorrect stock history is much harder to repair.

03Developer infrastructure8 min read

Building a CI/CD runner from scratch changes how you see pipelines

A pipeline is not just a YAML file. Behind it are signed webhooks, durable jobs, isolated execution, streamed logs, cancellation, timeouts, and state transitions that must survive restarts.

Building RunXR made those boundaries visible. The runner should remain simple, the queue should own work state, and the dashboard should report reality rather than inventing it from incomplete events.

04Security tooling5 min read

Secret management should fit the developer workflow

Security tools lose value when the safe path is slower than copying a key into a local file. Encrypted storage matters, but so do environment boundaries, a predictable CLI, and a clear model for how secrets reach a process.

Evnar is built around that balance: strong defaults without hiding the workflow behind a black box.

05Applied AI7 min read

Local-first AI agents need more than a chat box

An agent becomes useful when its runtime, knowledge, memory, skills, corrections, and evaluations are understandable as separate parts. A chat interface alone cannot show why behavior changed or whether a correction actually improved anything.

Orvel treats those parts as explicit product surfaces so an agent can be taught, tested, and run across local or hosted models without losing its identity to one provider.
